# HashMap

## 용도
- **키-값 쌍** 저장 및 키 기반 빠른 조회·수정·삭제
- 빈도 계산, 그룹핑, 캐싱, 인덱싱 등 범용 맵
- 키 순서가 중요하지 않은 경우
- 내부: **배열(버킷) + 연결 리스트·Red-Black Tree** 구조  
  (Java 8+: 버킷당 8개 초과 시 TreeNode로 전환)

## 장점
| 항목 | 내용 |
|------|------|
| **get/put/remove 평균 O(1)** | 해시 함수로 버킷 위치 직접 계산 → 탐색 없음 |
| **null 키/값 허용** | `put(null, v)` 가능 (버킷 0에 저장) |
| **유연한 초기 용량** | `new HashMap<>(capacity, loadFactor)` 로 리해시 최소화 |

## 단점
| 항목 | 내용 |
|------|------|
| **순서 미보장** | 삽입 순서·키 정렬 순서 모두 보장 안 함 |
| **해시 충돌** | `hashCode()` 충돌 시 버킷 내 O(n)·O(log n) 탐색 |
| **리해시 비용** | 로드 팩터(기본 0.75) 초과 시 버킷 2배 확장·전체 재배치 |
| **동기화 없음** | 멀티스레드 환경에서 `ConcurrentHashMap` 사용 필요 |

## 성능

| 연산 | HashMap | TreeMap | 비고 |
|------|---------|---------|------|
| `get(k)` | **O(1) 평균** | O(log n) | 해시 버킷 접근 vs 트리 탐색 |
| `put(k,v)` | **O(1) 평균** | O(log n) | 해시 버킷 삽입 vs 트리 삽입 |
| `remove(k)` | **O(1) 평균** | O(log n) | 해시 버킷 제거 vs 트리 삭제 |
| `firstKey()` | X | **O(1)** | HashMap에 없는 기능 |
| `subMap(a,b)` | X | **O(log n)** | 범위 뷰 |
| 정렬 순회 | X | **O(n)** | HashMap은 정렬 순회 불가 |

> **결론**: 빠른 단건 조회·수정이 목적 → HashMap / 키 정렬·범위 검색 필요 → TreeMap  
> 순서 유지 필요 → LinkedHashMap / 멀티스레드 → ConcurrentHashMap

## 1. 해시란?

해시는 **임의 길이의 데이터를 고정된 크기의 값으로 변환하는 것**이다.  
보통 `hashCode()` 같은 해시 함수를 사용해서 값을 만들고, 이 값을 기반으로 저장 위치를 빠르게 찾는다.

예를 들어 `HashMap`은:

- 키(`key`)를 해시값으로 변환하고
- 그 해시값을 이용해
- 내부 배열의 특정 버킷(bucket) 위치를 찾는다

즉, 해시는 **"빠르게 위치를 찾기 위한 계산된 주소 비슷한 값"** 이라고 보면 된다.

---

## 2. 해시 충돌 이유?

해시 충돌은 **서로 다른 키가 같은 해시값(또는 같은 버킷 위치)** 으로 매핑되는 현상이다.

이유는 단순하다:

- 키의 종류는 거의 무한히 많을 수 있는데
- 해시값이나 버킷 개수는 유한하다

그래서 서로 다른 두 키가 같은 위치로 들어갈 수밖에 없다.

예시:

- `"ABC"`의 해시값
- `"XYZ"`의 해시값

이 둘이 최종적으로 같은 버킷 인덱스로 계산되면 충돌이다.

즉, 충돌은 **해시가 이상해서만 생기는 게 아니라, 구조적으로 피할 수 없는 현상**이다.

---

## 3. HashMap은 어떻게 해결하는지?

Java의 `HashMap`은 해시 충돌을 **버킷 내부에서 추가 비교** 하는 방식으로 해결한다.

### 기본 방식: 버킷 내부에 여러 엔트리 저장
같은 버킷에 들어온 데이터들을 그냥 하나만 두는 게 아니라,  
**연결 리스트(Linked List)** 형태로 이어서 저장한다.

그래서 충돌이 나면:

1. 같은 버킷으로 이동
2. 그 안에 있는 엔트리들을 순회
3. `equals()`로 진짜 같은 키인지 비교
4. 있으면 값 수정, 없으면 새로 추가

### Java 8 이후 개선
충돌이 너무 많아져서 한 버킷에 데이터가 많이 쌓이면,  
연결 리스트 대신 **Red-Black Tree** 로 바꾼다.

- 적을 때: 연결 리스트
- 많아질 때: 트리로 변환

이렇게 하면 최악의 탐색 성능이 줄어든다.

- 리스트일 때: `O(n)`
- 트리일 때: `O(log n)`

## 4. 리해싱(Rehashing)으로 충돌 완화

리해싱은 충돌을 **직접 해결**하는 게 아니라, 충돌이 **덜 일어나도록 예방**하는 메커니즘이다.

### 동작 방식
1. `put()` 호출 시 현재 `size / capacity` 로 로드 팩터를 계산
2. 로드 팩터가 임계값(기본 **0.75**) 초과 시 버킷 배열을 **2배**로 확장
3. 기존 모든 엔트리를 새 배열 크기 기준으로 **재배치(rehash)**

```
버킷 16개, 엔트리 12개 → 로드 팩터 0.75 초과
→ 버킷 32개로 확장 → 전체 엔트리 재배치
```

### 충돌을 줄이는 이유
버킷이 많아질수록 같은 해시값이 같은 버킷으로 몰릴 확률이 낮아진다.  
즉, 충돌 자체가 줄고 → 버킷 내 리스트·트리 탐색이 짧아진다.

### 체이닝과의 차이
| 구분 | 체이닝 | 리해싱 |
|------|--------|--------|
| 목적 | 이미 발생한 충돌 처리 | 충돌 빈도 자체를 낮춤 |
| 시점 | 충돌 발생 시 즉시 | 로드 팩터 초과 시 |
| 비용 | 탐색 O(n) or O(log n) | 전체 재배치 O(n) |

> **실무 팁**: 저장할 데이터 크기를 미리 알면 `new HashMap<>(initialCapacity)` 로  
> 리해싱 횟수를 줄여 성능을 높일 수 있다.

---

## 핵심 요약

- **해시**: 데이터를 빠르게 찾기 위해 만든 계산된 값
- **해시 충돌**: 다른 키가 같은 버킷으로 들어가는 현상
- **HashMap 해결 방식**:
  - 기본은 **연결 리스트**
  - 많이 충돌하면 **트리(Red-Black Tree)** 로 전환
  - 최종 비교는 `equals()` 로 수행
